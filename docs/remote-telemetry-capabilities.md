## Sources

The existing adapter uses the following authenticated portal routes; this is a description of repository behavior, not an official API stability guarantee:

| Source                                                                                       | Purpose and scope                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `https://api.starlink.com/auth-rp/auth/user`                                                 | Session/identity refresh. Each credential has independent cached access state; the current client uses a 60-second cache and one forced refresh/retry on session expiry. This cache interval is not evidence of the upstream token lifetime. |
| `/webagg/v2/accounts/service-lines?limit=100&page=N&…`                                       | Service inventory. Reads `content.results`, account/service references and optional `content.totalCount`. Without a total, a short page terminates enumeration.                                                                              |
| `/webagg/v2/accounts/service-line/{serviceLineNumber}`                                       | Service details and terminal/router membership; nickname, optional formatted address and serial metadata. Two detail requests maximum in flight.                                                                                             |
| `/device-data/cache/v1/telemetry`                                                            | Account-wide cached telemetry requested with `accountNumber`. The Stage 1 read route filters results to the explicitly selected terminal and its known routers.                                                                              |
| `/telemetryagg/v1/data-usage/account/{accountId}/service-line/{serviceLineNumber}/annotated` | Selected service usage route exists and is tested synthetically. Live payload, units and historical coverage have not been verified.                                                                                                         |

Inventory discovers account references actually returned by the list plus the auth identity. It cannot infer additional empty accounts or undocumented account-switch behavior. Separate login sessions are supported; switching between several upstream accounts within one login remains unverified.

## Mapped metric matrix

Telemetry rows are decoded by names in `data.columnNamesByDeviceType`, with values in `data.values`. Device type `u` is decoded as a dish and `r` as a router. All rows below were present in the inspected Account B result. None constitutes a historical series.

| Device / metric        | Portal legend            | Current public field / type         | Units and semantics                                                           | Availability / presentation contract                                                                                           |
| ---------------------- | ------------------------ | ----------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Both: device identity  | `DeviceId`               | Record key / string                 | Stable device reference within the selected account context                   | Validate against selected service membership; do not use as a global account-independent key.                                  |
| Both: observation time | `UtcTimestampNs`         | `timestampMs` / number              | Client divides presumed Unix nanoseconds by 1,000,000 to produce milliseconds | Present in inspected rows; actual clock accuracy and update cadence unverified. Unknown/invalid time must not imply freshness. |
| Dish: software         | `RunningSoftwareVersion` | `softwareVersion` / string expected | Version label                                                                 | Display when present.                                                                                                          |
| Dish: uptime           | `Uptime`                 | `uptimeS` / number                  | Existing client interprets as seconds; not independently timed                | Snapshot counter, not a computed availability percentage.                                                                      |
| Dish: obstruction      | `ObstructionPercentTime` | `obstructionPct` / number           | Raw upstream scale and measurement window unverified                          | Do not append `%` or rescale until confirmed. A zero sample cannot distinguish a fraction from percent.                        |
| Dish: signal           | `SignalQuality`          | `signalQuality` / number            | Raw dimensionless value; range and physical meaning unverified                | Do not turn into a percentage, dB or a connectivity verdict.                                                                   |
| Router: hardware       | `WifiHardwareVersion`    | `hardwareVersion` / string expected | Hardware version label                                                        | Optional; known router membership required.                                                                                    |
| Router: software       | `WifiSoftwareVersion`    | `softwareVersion` / string expected | Software version label                                                        | Optional.                                                                                                                      |

The current legacy decoder converts numeric `null`, empty strings and booleans with `Number(...)`, defaults absent timestamps to zero, and maps an absent mode flag to false. These behaviors must not be carried into Stage 2 snapshots: accept only valid values, preserve valid numeric zero, represent missing data explicitly, and validate text/boolean types. This is a source-audit finding and an explicit S2.1 requirement; no evidence is claimed that these malformed values occurred in the live result.

## Initial proposal and current scope gate

The original proposal used inventory and mapped optional snapshots. The user subsequently made explicit status, current warnings and obstruction/alignment essential. That expanded contract cannot yet be considered verified; see S0.4 gaps below. Show source `cloud`, upstream observation time when valid, local fetch time, last successful fetch and the refresh/error state separately. An old cloud observation or missing LAN connection does not prove the dish is offline. Keep raw values labelled where units remain unverified; omit unsupported charts and controls.

Stage 2 adds account-scoped collection, scheduled refresh and persisted snapshots. It must fetch telemetry once per account per cycle, distribute rows by verified membership, and tolerate missing or reordered columns. The proposed defaults remain two-hour refresh, global concurrency two, one job per credential, a five-minute manual cooldown, and upstream backoff taking precedence. None has yet been exercised as a live scheduler.

S0.3 remains open for explicit resolution of the essential field gaps. Do not silently substitute signal quality for alignment or freshness for online/offline. Further read-only source verification is preferred before reducing scope; an on-site collector would require separate approval.

The local alignment implementation (`src/components/alignment/alignmentMath.ts`) consumes current and desired boresight angles plus alignment-estimation metadata, rather than the cloud `SignalQuality` scalar. Starlink's [Standard 4 installation guide](https://starlink.com/public-files/installation_guide_standard4_kit.pdf), page 5, also describes a separate alignment alert/tool. That confirms the concepts are separate; it does not document this portal feed's alignment schema. Official-site searches did not establish numeric `ActiveAlerts` mappings, status enums, or the obstruction field's units/window.

Starlink's public [dashboard metric guide](https://starlink.com/support/article/6aff51c6-254a-700e-c175-4c05a2b8c894//) describes displayed signal quality as a percentage representing SNR and obstruction as a percentage. This supports the concepts, but does not establish whether the raw portal columns already use percent or require scaling. Its [telemetry alert guide](https://starlink.com/vn/support/article/413011a8-34c9-5b33-bf97-03f7ca7273ea) documents named alert categories, including alignment and obstruction conditions, without a verified numeric-ID mapping to the observed arrays. Public help text is useful context, not permission to assume this session-backed feed matches an Enterprise API schema. No Enterprise API credentials or access were requested or used.

### Additional columns discovered, without expanding scope

Both dish telemetry legends also expose numeric `DownlinkThroughput`, `UplinkThroughput`, `PingDropRateAvg` and `PingLatencyMsAvg`. Router legends include numeric internet/POP/dish ping metrics, WAN byte counters and per-band client counts. Several optional per-band rate/signal columns were null or a mixture of null and number. Their precise units, windows and counter semantics are not verified here. These are potential later readings, not implemented functionality or a reason to expand the user's essential release automatically. Fields relating to location were neither retained as values nor proposed for display.
